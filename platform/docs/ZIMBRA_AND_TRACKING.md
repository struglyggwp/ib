# Тестовая почта, Zimbra и регистрация учебных переходов

## 1. Что реально установлено

В compose предусмотрен дополнительный **Mailpit** (режим `mailtest`) с SMTP и веб-почтовым ящиком. Mailpit — изолированный перехватчик тестовых писем, **не Zimbra**. Платформа также умеет подключаться к **уже установленной Zimbra** или иному SMTP по заданному хосту/порту, проверять TLS/SMTP-AUTH и отправлять одно безопасное тестовое письмо только по allowlist.

Полноценная Zimbra **не разворачивается** из этого Compose: для текущей Zimbra 10.1 нужен отдельный поддерживаемый Linux-хост/VM, DNS (A/MX), ресурсы (ориентир от 8 ГБ RAM и 50 ГБ диска), лицензирование и установка штатным дистрибутивом. Она конфликтует с Nginx/БД/MTA, если ставить в одну ОС. См. официальное руководство: https://zimbra.github.io/documentation/zimbra-10/single-server-install.html

Устаревший тестовый репозиторий `Zimbra/docker-zcs-foss` использует версию 8.8.3 и не является современным воспроизводимым образом Zimbra 10.1.

## 2. Быстрый локальный SMTP-тест (без Zimbra)

1. В `.env` добавьте настройки:

```env
SMTP_HOST=mailpit
SMTP_PORT=1025
SMTP_USE_STARTTLS=0
SMTP_USE_SSL=0
SMTP_USERNAME=
SMTP_PASSWORD=
SMTP_FROM_EMAIL=training@training.test
SMTP_TEST_RECIPIENTS=tester@training.test
```

2. Выполните (с тем же Compose project, что и при текущем запуске):

```powershell
docker compose -p security_awareness_platform_v0_13 --profile mailtest up -d --build
```

**Важно**: `-p security_awareness_platform_v0_13` здесь лишь пример, замените на фактическое прежнее имя проекта, иначе PostgreSQL подключится к *другому* тому. Проверить: `docker compose ls`, `docker volume ls`.

3. Откройте `http://127.0.0.1:8025/` и `http://127.0.0.1:8080/campaigns/mail/`. Нажмите **Проверить SMTP и вход**, затем выберите `tester@training.test` и **Отправить тест**. Письмо должно быть видно в Mailpit, но наружу не доставляется.

4. При изменении `.env` Docker Compose нужно пересоздать `web`: `docker compose -p <project> up -d --force-recreate web`. Не надо использовать `down -v`.

## 3. Подключение своей тестовой Zimbra

1. Разверните Zimbra **на отдельной VM**, по официальной инструкции, с разрешённым доменом, A/MX DNS, отдельным IP и сертификатом TLS. Нужна действующая лицензия для редакции, если она требуется.
2. Создайте только тестовые почтовые ящики (например, `security-test@lab.example.com` и `receiver@lab.example.com`).
3. В `.env` платформы укажите:

```env
SMTP_HOST=mail.lab.example.com
SMTP_PORT=587
SMTP_USE_STARTTLS=1
SMTP_USE_SSL=0
SMTP_USERNAME=security-test@lab.example.com
SMTP_PASSWORD=your-SMTP-app-password
SMTP_FROM_EMAIL=security-test@lab.example.com
SMTP_TEST_RECIPIENTS=receiver@lab.example.com
```

4. Пересоздайте `web` командой `docker compose -p <existing-project> up -d --force-recreate web`, проверьте https://your-platform-host/campaigns/mail/.
5. Для локального теста на компьютере разработчика — http://127.0.0.1:8080/campaigns/mail/. В приложении **нет автоматической рассылки кампаний**.

Настройте сетевой доступ к Zimbra: исходящий TCP/587 от Docker-host, правильно разрешающееся имя и доверенный TLS-сертификат. Проверка SMTP handshake означает лишь доступность и успешную аутентификацию; для проверки доставки нужен тестовый ящик. В случае Zimbra не публикуйте порт админки 7071 или LDAP наружу без отдельной политики безопасности.

## 4. Как происходит регистрация перехода

- Оператор готовит кампанию со снимком аудитории и нажимает **Создать ссылки**.
- У каждого участника своя ссылка вида `https://platform.example.com/learn/<uuid>/`.
- При HTTP GET сервер находит `TrainingLink` и `CampaignParticipant → Employee`, если ссылка не отозвана, срок не истёк и кампания имеет статус `approved/running`.
- В PostgreSQL записывается `ParticipantEvent(link_visited, occurred_at)` по часовому времени сервера (UTC в базе, локальное в интерфейсе).
- Нажатие на единственную кнопку ознакомления создаёт `ParticipantEvent(training_completed)`; секреты/значения полей формы не хранятся.
- По одному событию на пятиминутный слот. Не сохраняются IP, User-Agent или содержимое формы.
- `prefetch/prerender` по служебным заголовкам не фиксируются, но сторонние сканеры иногда выглядят как обычные браузеры.

### Ограничения достоверности

Ссылка привязывает запрос к предполагаемому адресату, но не доказывает, кто нажал на неё: она могла быть переслана, скопирована, открыта антивирусом или почтовым сканером. Для подтверждённой личности необходима аутентификация. `message_opened` отсутствует: переход по ссылке нельзя выдавать за открытие письма. Старые анонимные `SafeEvent` не входят в именной отчёт.

### Правовые и сетевые требования

Используйте только согласованные учения в собственном домене/с разрешения организации; предупредите участников согласно внутренней политике, определите сроки хранения и доступ к персональным результатам. Для переходов с чужих компьютеров адрес `127.0.0.1:8080` не подходит: понадобится доступный по сети URL с HTTPS, DNS и корректными `DJANGO_ALLOWED_HOSTS`/`DJANGO_CSRF_TRUSTED_ORIGINS`. Не делайте интернет-доступным тестовый Mailpit. Не включайте реальные поля ввода паролей.
